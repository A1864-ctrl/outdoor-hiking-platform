01一、核心结论

在逐项比对之前，先给出五条结论。后续章节是对这五条结论的论证与落地设计。

（一）两个仓库是同一个项目，不是两个项目

两个仓库的文件清单、字节数完全一致：Home.py 847 B、app_utils.py 15,559 B、gpx_store.py 11,691 B、README.md 14,757 B、requirements.txt 728 B，data/、views/、tools/、screenshots/ 目录结构相同。唯一的差异是 python 仓多了一个 _archive-early-vue/ 目录和一份《说明-本地存档.md》。也就是说，所谓"两个项目整合"，实际是"一个项目 + 一份带 Vue 试验残留的存档"。python 仓的存档说明自己也写明了两者"代码独立、数据独立"，实为同一份代码的两次快照。

因此整合的第一步不是合并，而是去重：以 streamlit 仓为主干，python 仓只保留《说明-本地存档.md》作为资料留痕，源码与数据不重复保留，_archive-early-vue/ 直接删除——它含 Vue 3 + Vite，违反"只能使用 Python 和 MySQL"的硬约束。

（二）现有项目是"只读看板"，不是"平台"，缺口在 6/8

这个项目做得很扎实：155 个景点、34 条路线、15,330 个真实轨迹坐标点，3,708 行代码，还有一条 OSM → Valhalla 路网 → SRTM 高程的离线数据流水线。但它的形态是"Streamlit 单脚本 + pandas 读 CSV + 按热度排序"，没有用户、没有数据库、没有内容生产、没有后台。对照任务书八项主要任务，现成能满足的只有第（1）项景点浏览和第（2）项路线库；第（3）至（8）项——推荐、路书、收藏评价、个人中心、后台、账户安全——全部为零。

这意味着整合的重心不在"拼接"，而在"补壳"：把已有的数据与几何算法当作底座，在外面重建一套带用户体系、带 MySQL、带后台的平台。工作量分布大约是"数据与算法 20%、平台功能 80%"。

（三）技术路线必须二选一，且任务书现有表述要改

现在存在两个互相打架的方案：桌面那份《内容说明与技术方案》写的是 Django MVT + 模板渲染，而《任务书_模板填写版》写的是"前端 Streamlit，后端 FastAPI + Uvicorn"。两者不能同时成立，而且都不理想：Django 的 MVT 与任务书要求的"四层架构 + 接口层 + 接口文档"表述对不上；Streamlit 根本承载不了注册登录、多用户会话、内容审核和接口文档。

建议裁决为 FastAPI + Jinja2 模板 + MySQL 8.0，理由见第四章。同时任务书里"前端 Streamlit"这一句需要改成"前端 Jinja2 模板 + Bootstrap 5"——这是任务书定稿前必须改的一处硬伤，否则开题材料与最终成果自相矛盾。

（四）功能范围要按任务书收敛，不能按原方案文档铺开

原方案文档写了景点、路线、路书、社区帖子、评论点赞、搭子组队、举报、站内通知、天气、地图等十余个模块，比任务书的八项任务多出近一倍。这些多出来的模块（社区发帖、组队、举报、通知、天气）在任务书里没有对应条款，做成半成品反而会在答辩时被追问"哪些是核心"。建议一律列为"不纳入本期"，把省下的时间投到推荐算法的可解释性和数据质量上。

（五）数据库要精确落在 12 张表

任务书白纸黑字承诺"设计 12 张表并编写建表脚本"，这是要兑现的硬指标。现有项目 0 张表，需要全新设计。本方案给出恰好 12 张核心表的完整设计（第八章），并把 E-R 关系、字段、索引、以及三个必须写进论文的设计权衡一并给出。

（三）数据资产的可用性核查

数据是这份材料最大的价值，但直接入库会踩坑。逐表核查后，有四个问题必须在迁移阶段处理。

1. 路线类型没有归一，25 种取值里有同义重复

34 条路线的 type 字段统计出 25 种不同取值，其中"山岳"6 条、"丹霞地貌"与"丹霞"并存、"田园"与"乡村田园"并存、"花岗岩"与"花岗岩峰林"并存。如果直接把这个字段当分类用，前台筛选会出现"丹霞"筛不到"丹霞地貌"的问题。必须建 category 字典表，迁移时做一次映射归一。

2. 城市名口径不一致，景点用短名、路线用全称

景点表 city 是"广州""深圳"，路线表 city 是"深圳市大鹏新区""衡阳市南岳区"。现有代码用 norm_city() 截取"市"之前的字符串硬凑（见 views/热度榜.py），这是绕不过去的补丁。正确做法是建 region 维表，景点和路线都存 region_id，彻底消除字符串匹配。这也是把"代码补丁"升级为"数据库设计"的一个好例子，答辩时可以讲。

3. 最佳季节是自由文本，且存在跨年区间

best_season 的取值有"5-10月""4-11月""10-5月""全年"等，其中"10-5月"是跨年区间（10 月到次年 5 月）。做季节匹配时如果按 start ≤ month ≤ end 判断，跨年路线会永远匹配不上。需要在迁移时解析成 season_start / season_end 两个整数月字段，并在算法里对 start > end 的情况走环形区间判断。

4. 字段有缺口，且部分空缺需要补

景点表 13 个字段能覆盖任务书要求的名称、等级、门票、建议时长、最佳季节、特色、经纬度、热度，但缺"地址、开放时间、游览提示、封面图"。路线表 17 个字段覆盖里程、爬升、最高海拔、难度、耗时、季节、描述，但缺"累计下降、最低海拔、交通方式、补给建议、安全提示"。

好消息是累计下降和最低海拔不用手填——轨迹 JSON 的 stats 里已经有 descent_m 和 ele_min，迁移脚本读出来回填即可。剩下的文字类字段（交通、补给、安全提示）建议只给热度前 20 条补全，其余留空并在前台做空值兜底，避免为了填满字段耗掉两周。

（二）选定方案与四条理由

裁决为方案 C：FastAPI + Jinja2 模板 + MySQL 8.0 + SQLAlchemy 2.0 + PyMySQL。

理由一，四层架构能逐层落地。表现层是 Jinja2 模板与静态资源，接口层是 FastAPI 路由，服务层是业务函数，数据层是 SQLAlchemy 模型与会话。任务书要求"按数据层、服务层、接口层、表现层顺序分模块开发"，这个结构可以原样对应，论文里画架构图也不用硬凑。

理由二，接口文档与接口测试用例是任务书明确的预期成果。FastAPI 自带 OpenAPI，访问 /docs 即可导出接口文档；pytest 配合 TestClient 写用例，天然就是"接口测试用例及执行记录"。这一条在 Streamlit 方案下根本无法交付。

理由三，后台管理必须自己写。Django Admin 虽然省事，但答辩时评委看到"后台是框架送的"，会直接质疑工作量与设计能力。FastAPI 方案下后台的列表、筛选、审核、统计都要自己实现，这部分恰恰是能讲清楚"我做了什么"的地方。

理由四，只有一个 Python 进程。没有 Node、没有 npm、没有构建产物，部署就是 Gunicorn 起一个进程，既贴合"只用 Python"的约束，也降低了云端部署的失败率。

需要接受的代价

Jinja2 模板意味着列表页、表单页、详情页都要手写 HTML，页面工作量比 Streamlit 高出一个量级。缓解办法有三条：一是统一 base.html 与组件宏，把导航、卡片、分页、表单控件做成 macro；二是列表页用服务端分页而不做无限滚动；三是只对收藏、点赞这类轻交互用 fetch 局部刷新，其余走整页跳转。按这个策略，12 个页面的模板工作量可以控制在可接受范围。

（二）四条主流程

1. 找路线：从筛选到出发

游客进入首页 → 看到热门路线与推荐入口 → 进入路线库，按省份、难度、里程区间筛选 → 点开详情，看轨迹地图、高程剖面、途经点与安全提示 → 若已登录，可点"收藏"或"写评价"。若从"推荐"进入，则先填三个偏好（难度、里程上限、出行月份），系统返回 Top10 与理由，再点进详情。这条流程的关键是：游客也能看到推荐结果，用一组默认偏好兜底，降低首次使用门槛。

2. 发路书：从写完到上线

登录用户点"发布路书" → 填写标题、出行日期、天数、交通、费用、装备、注意事项与正文 → 选择关联路线（可从已浏览过的路线里选，也可不关联）→ 可选上传 GPX 轨迹文件作为实证 → 提交后状态为"待审核"，本人在个人中心可见 → 管理员在后台审核，通过则前台可见，驳回则填写原因 → 作者可编辑后重新提交。审核状态用 0 待审、1 通过、2 驳回三个值，不用布尔字段。

3. 评价回流：让分数影响推荐

用户完成徒步后在路线详情页打分（风景、难度、交通、整体四项，1~5 分）→ 服务层写入 route_review → 同时重算该路线的加权平均分（含贝叶斯平滑，见第九章）→ 下次任何人请求推荐时，评分因子 R 使用最新值。这条闭环是"评价"与"推荐"两个功能之间的连接点，也是论文里可以画一张数据流图的地方。新路线评价数为 0 时，平滑公式会把它拉向全局均值，避免冷启动被埋没。

4. 后台治理：审核与统计

管理员登录 → 进入后台首页看统计卡（用户数、景点数、路线数、路书数、评价数、待审路书数）→ 进入路书审核列表，按状态筛选，逐条通过或驳回 → 进入路线管理，编辑难度、季节、安全提示 → 进入用户管理，禁用违规账号。所有写操作记录操作人与时间，便于追溯。

（五）三个必须写进论文的设计权衡

1. 轨迹点为什么不入库

34 条路线共 15,330 个坐标点。如果建 route_track_point 表逐点存储，全表约 1.5 万行、每行 6 个字段，看似不多，但会带来三个后果：一是每次看路线详情要拉取数百行做拼接，查询开销远高于读一个 JSON 文件；二是数据库备份体积膨胀、迁移变慢；三是没有任何"按单点查询"的业务需求。因此采用"元数据入库、几何数据留文件"的方案：hiking_route 存 track_file 路径与统计摘要，轨迹点保留原 JSON 结构。这也让 12 张表的承诺得以守住。论文里要把这个取舍写清楚，并说明触发条件——如果将来需要按空间范围检索轨迹，再拆出轨迹点表并用空间索引。

2. 多态关联为什么不做外键

comment 和 favorite 要同时指向景点、路线、路书三类对象。规范做法是拆成三张表，在 12 张表的约束下不可行；替代做法是 target_type + target_id 的多态关联。代价是数据库无法用外键保证引用完整性，被收藏的对象删除后会留下孤儿记录。解决办法是在服务层统一提供"清理钩子"：任何内容被删除时，同步删除对应的 favorite 与 comment。这是一个典型的"用应用层约束换表数量"的权衡，答辩时主动讲出来，比被问出来好。

3. 地区为什么单独建表

现有代码用 norm_city() 截字符串解决"深圳"与"深圳市大鹏新区"的匹配问题。这种补丁在数据量小的时候能跑，但一旦要做"按城市聚合统计""按城市推荐"就会到处漏。建 region 表后，景点和路线都只存 region_id，城市名归一只做一次（在导入脚本里），后续所有查询与统计都靠整数关联，既快又不会错。这是把"代码技巧"升级为"数据建模"的典型案例。

10十、路线推荐算法设计

这是课题的题眼，也是现有项目与任务书差距最大的一块。现有代码只有一句 sort_values("heat", ascending=False)，这不叫推荐，叫排序。本章给出可直接实现的算法。

（一）两段式结构：先硬过滤，再加权打分

把"不合适的"和"次优的"分开处理。第一步用硬条件把不可能的路线剔掉，第二步在剩余候选里打分排序。这样既能保证结果都可用，又能让打分公式专注于区分优劣。

候选集 = { r | r.status = 1
             ∧ r.region_id ∈ 用户可选地区
             ∧ r.distance_km ≤ 用户里程上限
             ∧ 季节区间与出行月份有交集 }

对候选集内每条路线 r：
    Fit(r) = wD·D(r) + wL·L(r) + wS·S(r) + wR·R(r) + wH·H(r)
按 Fit 降序取 Top10，为每条生成中文理由

（二）五个因子的定义

表 10.1 推荐因子定义与计算方式

因子含义取值范围计算方式
D 难度匹配路线难度与用户偏好难度的接近程度0~1D = 1 − |difficulty − prefer| / 4。偏好为"不限"时统一取 0.8，避免压制
L 里程匹配路线里程在用户可接受范围内的利用度0~1L = min(distance_km, max_km) / max_km。太短扣分，超限已在硬过滤阶段剔除
S 季节匹配出行月份是否落在最佳季节内0~1命中区间取 1.0；相差 1 个月取 0.6；相差 2 个月取 0.3；其余 0.1；"全年"取 0.9。跨年区间（start > end）用环形判断：m ≥ start ∨ m ≤ end
R 评分质量其他用户对该路线的评价水平0~1贝叶斯平滑后除以 5，见下文公式
H 热度路线受关注程度0~1H = heat / 100，直接用现有字段

（三）评分要平滑，否则新路线永远排不上

直接用 rating_avg 会出问题：一条只有 1 个 5 分评价的新路线，均分 5.0，会压过有 50 个评价、均分 4.6 的老路线。解决办法是贝叶斯平均（与 IMDb 的电影排名同一思路），把评价数少的对象向全局均值收缩：

R_smooth = (v / (v + m)) · R_avg  +  (m / (v + m)) · C

  v = 该路线的评价数 (rating_count)
  R_avg = 该路线的算术均分
  C = 全站所有路线的评价均值（初始化时取 4.0）
  m = 平滑强度常数，取 5（相当于"先给它 5 个均分评价"作为先验）

效果：评价数 0 时 R_smooth 等于全局均值，不会被埋没也不会虚高；评价数到 20 条以上时基本等于真实均分。这个公式解释起来简单，实现只有三行，但能明显体现"想过边界情况"，是论文里值得单独写一段的点。

（四）权重与理由生成

表 10.2 权重取值与来由

因子权重取值理由
D 难度0.25难度不匹配是户外最大的体验风险，权重最高
L 里程0.20体力与时间的硬约束，但已在过滤阶段起作用，故不最高
S 季节0.20华南山区季节差异极大（草甸封山、海岸线台风），必须重视
R 评分0.20他人经验是可信度最高的信号，但样本少，与季节同权
H 热度0.15热度是外部指标，容易与真实质量脱节，权重最低

五个权重之和为 1，写在 config.py 里可调。论文里要说明这是经验取值，并给出一次权重敏感性实验：固定其他条件，只改某一权重，观察 Top10 的变化，用表格呈现。这是让"规则推荐"看起来有实验支撑的最省力办法。

推荐理由不写"匹配度 87 分"这种机器语言，而是取贡献最大的两个因子拼成一句话。规则如下：

按 w_i·F_i 排序，取贡献最高的两个因子，套模板：

  D 最大 → "你偏好{难度}难度，这条正好是{difficulty}"
  L 最大 → "全程{distance}公里，在你设定的{max_km}公里以内"
  S 最大 → "{month}月正合适，最佳季节是{season}"
  R 最大 → "{count}位用户平均打了{avg}分"
  H 最大 → "近期热度{heat}，是本区域的热门线路"

输出示例：
  "你偏好中等难度，这条正好是中等；全程 8.6 公里，在你设定的 10 公里以内。"
  "5 月正合适，最佳季节是 4-11 月；12 位用户平均打了 4.6 分。"

这样做的好处是：用户知道"为什么推荐给我"，评委也能顺着理由反推算法是否正确。比单纯给一个分数要有说服力得多，这也是"S1 推荐理由生成"作为特色功能的支撑点。

（五）游客怎么办

未登录用户没有偏好数据。三种处理方式里，选第三种：一是直接不给推荐（体验差）；二是要求先登录（掉转化）；三是用一组默认偏好兜底——难度取"中等"、里程上限 15 km、季节取当前月份，并在页面顶部提示"这是通用推荐，登录后可按你的偏好调整"。这个细节体现了对未登录场景的考虑，写进论文不占篇幅但有效。

（六）可测试性

算法要能被单测，就得把打分函数写成纯函数：输入一条路线对象和一组偏好，输出分数与理由，不碰数据库。这样 tests/test_recommend.py 可以构造边界用例：难度完全一致时 D=1；里程超限已在候选集外；跨年季节 10-5 月在 12 月能命中；评价数为 0 时 R 等于全局均值。四个用例覆盖了最容易出错的地方，也正好是测试章节的素材。

15十五、需要你确认的三件事

方案里有三处是"我认为该这样"，但最终要你或指导老师拍板。

1. 技术栈从 Streamlit 改为 Jinja2 模板，任务书要跟着改

这是影响最大的一处。如果你倾向于保留 Streamlit（比如已经比较熟），那必须接受两个后果：一是做不出带权限的后台，二是交不出"接口文档与接口测试用例"。如果指导老师对这两项不较真，Streamlit 方案能省下大量页面工作；如果较真，就必须换。我的判断是换，因为任务书写得很明确。

2. 12 张表是否必须严格等于 12

本方案设计成恰好 12 张，是为了对上任务书的承诺。如果你在实际开发中发现确实需要第 13 张（比如操作日志表），有两个处理方式：一是在说明书里写"12 张核心表 + 1 张日志表"，并说明日志表不属于业务模型；二是把日志写文件而不入库。前者更规范，后者更省事。

3. 数据缺口补到什么程度

景点缺地址、开放时间、游览提示、封面图；路线缺交通、补给、安全提示。全部 155 条补全大约需要 3~4 天。建议只补热度前 20 条，其余留空并在前台做兜底显示。如果你希望页面看起来更完整，可以只补"安全提示"这一类——它对徒步场景最有价值，也最能体现专业性。
